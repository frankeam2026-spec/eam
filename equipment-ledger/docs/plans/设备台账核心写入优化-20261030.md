# 设备台账核心写入优化

日期：2026-10-30。依据《后端开发规范 v1.0》，延续此前设备查询与领料草稿整改；本批聚焦设备核心写入及负责人读写，不改变数据库结构或UI布局。

## 需求追踪与设计边界

| 场景 | 入口/实现 | 验收条件 |
|---|---|---|
| 新增、完整修改、基础信息分区修改 | EquipmentCommandService.create/update/updateDetails；EquipmentInputValidation | 正常保存兼容；编辑与新增同样检查长度、精度、关联ID及实体展示字段 |
| 负责人维护 | EquipmentWriteRepository及CommandService | 固定负责人投影使用Long和明确名称；保留顺序、去重、停用旧负责人保留及清空语义 |
| 依赖及状态校验 | CommandService构造器及InputValidation | 必需依赖final；状态配置只有一个解析来源，仍允许项目配置的状态 |
| 响应封装 | EquipmentController、EquipmentQueryController | 复用DataResponse，原路由及JSON形状保持；删除/批量结果显式建模 |
| ID精确性 | EquipmentForm的Long及ID集合绑定 | 字符串和整数兼容；小数、布尔、溢出及非法关联ID定位到字段并返回400 |
| 事务中的当前设备 | EquipmentWriteRepository.find | 核对独立BOM保存后版本，以及JDBC变更后当前名称；两个反例均通过，保留原读取策略 |
| 权限、版本及分区边界 | 既有权限检查、公司锁、VersionGuard及分区保存 | 拒绝越权、冲突与跨公司关联；核心保存不修改独立关系；持久化后失败整体回滚 |

根因证据：create调用了完整输入及实体校验，updateInternal缺少这两步；负责人通过Map及字符串键装配；独立关系通过JDBC递增版本，随后设备读取可能重用MyBatis会话缓存，需要数据库反例确认。测试先记录旧实现表现，再检查修复结果。

复用现有Service、输入校验器、MyBatis-Plus、公司/库存互斥锁、附件和扩展字段服务。公司、部门、权限、版本及更新事务仍由原业务入口承担，不增加第二套权威。

范围内不迁移JSON存储、不改变关系或附件的既有协议、不改导入暂存结构、不改变库存成本与锁粒度。EquipmentView中的旧关系/附件结构及自定义字段边界会如实登记，不以顶层包装改名宣称深层协议已全部整改。

## 已实现

- 编辑补齐与新增相同的基础输入、关联ID和实体展示字段校验。已用旧实现复现：121字符规格型号到SQL层才报截断；现在返回400的model字段错误。采购金额精度、是/否标志及完整位置路径同样在写入前检查。
- 负责人读写采用EquipmentOwnerSnapshot(Long id, String name)，消除固定数据的Map及字符串键转换。保留原负责人顺序、去重、清空和已停用/已删除原负责人的历史名称处理。
- CommandService必需依赖改为构造器注入；状态配置只由EquipmentInputValidation解析；字段长度校验显式调用，不再把固定字段临时塞入Map<String,Object>。
- 核心关联ID和负责人ID集合使用ExactLongDeserializer及正数/元素非空校验，兼容现有整数和字符串输入，拒绝小数截断、布尔和溢出。
- 固定成功响应复用DataResponse；删除与批量结果使用明确类型。保留原200状态和data、deleted、count字段。
- 附件序列化失败向上抛出，不再吞异常返回空数组；当前文件新增、修改的注释已使用中文。
