# 保养通知与事件归属整改（2026-11-12）

基线 `2256d30`，延续保养治理第2批，限通知、事件、已读、待办关闭及执行提醒查重。其他资料选择、任务状态机、生成算法和库存不在本批修改范围。

## 依据与实现

原MaintenanceRepository同时维护任务、事件、消息，并在insertInbox中跨仓储捕获公共通知，在softDeleteTask中隐藏消息更新。此次移除6个事件/消息方法、通知字段注入及删除任务中的消息更新（该类共减少88行），不保留旧方法转发。

| 场景 | 归属与设计 | 验收条件 |
|---|---|---|
| 消息登记及公共投递 | MaintenanceInbox Entity/Mapper/Repository；既有Journal Service协调inbox.insert和NotificationRepository.captureSource | 翻译键和参数直接随INSERT写入，公共捕获顺序不变；捕获失败，两侧记录与任务一起回滚 |
| 消息关闭与已读 | InboxRepository通过LambdaUpdateWrapper完成 | 流转只关闭待办；删除先按原流程关闭待办、再关闭全部消息并以COALESCE保留已有read_at；单条已读限定tenant/user/id |
| 提醒存在性 | GenerationService → Journal.hasExecutionNotice → InboxRepository.hasNotice | 包含已关闭及已读历史，不因默认追加done=0而重复提醒；统一复用本域EXECUTION_NOTICE编码 |
| 审计事件读写 | MaintenanceEvent Entity/Mapper/Repository | actorId允许null、数据库默认时间、同任务按created_at/id升序；无新增手写CRUD SQL |
| 事件展示与统计 | Journal返回MaintenanceTaskEventView，统计读取类型化action | 保留action/actor/time/details四字段、秒级时间文本，与原数据库DATE_FORMAT逐字核对 |

details仅是各动作不同的审计详情，保留历史JSON及动态对象；固定事件字段显式建模，不将任务核心字段塞进details。此例外不推广至其他固定Map接口。HTTP根任务响应的旧Map及工作台消息列表的跨表只读查询仍属存量，未宣称全模块类型治理完成。

技术取舍：复用MyBatis-Plus及现有通知捕获，不新建通用消息框架。涉及NOW和COALESCE的更新通过原生Wrapper静态setSql片段保留数据库时钟语义，其余均为类型化条件；没有用应用当前时间替代数据库时间。消息路由、接收人、抄送和渠道策略不变。Journal加入原任务事务，没有独立提交、异步化或网络发送。删除路径仍保持原来的两次消息更新及任务更新顺序。
