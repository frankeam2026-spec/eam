## 整改顺序与保留契约

1. **附件完整链路（本批）**：固定上传响应、单条元数据模型与自有 Repository、独立磁盘存储、失败清理；保留20MB/扩展名、UUID、响应五字段、上传者或可见单据引用的下载授权、MIME 与文件头。
2. **资料读取及履历/通知归属**：核查各表主要 Repository 与已有公共能力，消除保养仓储直接维护其他领域数据；先覆盖真实事务与现有通知入队，不改通知业务规则。
3. **定义与列表**：按类型、标准、计划分别做 DTO/Entity/Mapper 与关联装配，沿用列表/选择器/导出授权和筛选排序；用隔离库记录 SQL 次数和同条件结果。
4. **任务生成与执行写入**：显式命令及结果、参与人/执行/事件持久化归属、Service 事务编排；必须保留固定间隔与完成时间两种计时、提前生成、到期作废、验收打回、库存锁和幂等。不能强行与点巡检统一生成器。
5. **AI 只读边界**：复用已落地的类型化计划/授权模式，由保养模块执行查询；不经 Service 跨模块传 SQL。

每批独立验证和回退；本文件记录顺序，不以静态审查代替完整业务验收。不追加邮件/App、持续压测或独立审计。
