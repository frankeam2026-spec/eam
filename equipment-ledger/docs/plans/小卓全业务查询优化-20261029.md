# 小卓全业务查询优化与验收清单

日期：2026-10-29。状态：统一查询基础已实施，已验收与尚未接入范围见[实施记录](../features/小卓统一业务查询-20261029.md)。下列矩阵仍是完整目标，不能视为所有场景均已上线。依据：用户要求一次性考虑设备、维修、保养、点巡检等系统业务，避免逐个问句补丁。当前会话要求优先；工程索引见../engineering/README.md。

## 1. 当前证据与本次边界

代码已具有设备台账、维修工单、保养计划/任务、日常点检和周期巡检计划/任务、库存查询、工作台待办及审批运行能力。已有统计目录包括报修次数排名、报修与完成趋势、故障类型/原因、人员工作量、保养执行/部门对比、点巡检执行、异常次数和实际物料消耗等12项。它不是完整的自然语言业务查询目录。

小卓目前仅接入有限的设备数量/列表、维修记录以及现有指标；设备分组统计、保养和点巡检的自然语言明细等仍缺失。现有问题不只是关键词少，而是工具能力、语义目录与组合查询不足。

存储核查澄清：V67/V69已将保养和点巡检定义拆为关系表，V70将执行及结果明细关系化并删除两个任务表的result列，V79补齐任务项目/设备关系。v_maintenance_*、v_inspection_*中的payload/result主要是关系表生成的兼容查询投影，不应因查询使用JSON_EXTRACT就认定业务核心仍存于JSON。任务生成时的snapshot仍有保留，其用途及约束见../engineering/数据库关系化整改-20261018.md第49—63行。实施统计时可评估绕过“组装JSON再拆解”的查询成本，但不能把性能改进说成重做已完成的存储整改。本次源码核查时本地3306未监听，没有把旧验收记录当作当前实库验证结果。

本次必须做：统一的只读自然语言业务查询、系统已有数据可支持的筛选/汇总/分组/排序/对比、明细穿透、上下文追问、权限和成组验收。先对全部模块形成覆盖清单，再按依赖实施并整体交付；内部可分批建设，不能把某个问句跑通作为本轮交付完成。

数据不足的指标需要明确列为缺口，不伪造数值。审批办理、派工、修改计划、自动报修、自动补货等写操作不是本次查询授权范围。预测性维护、OEE、采购建议和自动决策属于有实际需求后另行确认的能力。

## 2. 客户问题矩阵

以下是需要覆盖或明确说明数据缺口的验收需求，不是当前可用功能宣传。

### 设备台账

- 数量与清单：我们有多少设备；有哪些冲压机；查一下闲置、停用、故障设备；P-103是什么型号、在哪里、谁负责。
- 分类统计：所有设备按分类统计报表；按公司、部门、设备状态、使用状态、品牌统计数量和占比；数量最多的前10个分类。
- 组合与排序：某部门在用设备按分类统计；今年购置的设备有哪些；按购置时间倒序；哪些设备即将到保修期或校准有效期。
- 明细：点某个分类、部门或状态查看对应设备，明细总数须与统计一致；同名组织/分类不能混并。

### 维修工单

- 当前事项：现在有哪些待派工、待接单、处理中、挂起、待验收的工单；我负责哪些；无人接单多久了。
- 历史查询：P-103最近三个月修过什么；上个月完成哪些工单；某维修人员的处理记录。
- 分组与排行：按部门/设备/故障类型/原因/维修人员统计；报修最多的设备；本月新增与完成趋势；与上月相比怎样。
- 时长与超期：哪些工单接单等候最长、处理等待最长；是否扣除挂起、按哪个轮次及哪些事件计算，复用真实业务事件，核对后才提供时长指标。
- 费用与用料：某设备维修实际用了哪些备件、数量和成本；实际消耗不能拿申请、预留、出库数量代替，人工/外协费用未核实不得合称完整维修总费用。
- MTTR/MTBF：列入指标缺口核查，实际维修时长、运行时长、独立故障事件及历史数据完整性确认前不计算。

### 保养

- 计划：哪些计划已启用/停用；计划覆盖哪些设备、执行人是谁；某设备采用什么保养标准。
- 任务：今天/本周应做、待执行、待验收、过期的任务；我负责的任务；某设备最近一次保养记录。
- 执行分析：本月完成、按时提交、逾期情况；按部门/负责人/设备/计划统计和排行；未执行最多的设备。
- 追溯：任务为什么延期或作废；是否提交、谁提交、谁验收；保养消耗哪些物料。
- 即将到期只查询真实已生成任务；对尚未生成的计划预测必须有可靠预览能力并明确标为预计，不能当作已有任务。

### 日常点检

- 今天各班次应检多少、已检多少、还有哪些没检；白班哪个设备未点检；现场开放任务有没有人执行。
- 我待执行/待审核的任务；昨天点检记录；某设备某一天哪个班次是谁点检的。
- 按计划/设备/班次/部门统计执行、逾期、异常；异常集中在哪些检查项目，哪些任务跳过项目。
- 查询异常结果、图片和后续处理关联；任务数量与检查项目数量分开，不能用未填的负责人代替实际点检人。
- 公司/部门按现有任务列表的计划所属部门口径；如用户明确问设备部门，必须另用明确维度，不能悄悄替换。

### 周期巡检

- 本周有哪些待巡检、过期、待审核任务；某条路线完成了吗；哪个检查点没有执行或出现异常。
- 按路线/计划/设备/部门/人员统计执行和异常；周期内的异常次数趋势；某设备历史巡检结果。
- 路线任务、设备、检查点、检查项目分别计数；一项异常不能因为连接多张明细表被重复累计。
- 与日常点检采用不同任务实体和时间/审核规则，只有在口径允许时显示并列或合计。

### 库存、领料与实际用料

- 某备件各仓库现存、已预留、可用分别多少；我的领料申请到哪一步；哪些已批准尚未出库。
- 某任务申请/发放/使用/安装/退回了哪些物料；按设备、任务、部门、仓库、物料统计实际消耗与排行。
- 哪些低于已配置安全库存、哪些长期没有流转：先核查阈值与流水字段；未维护阈值不假定缺料，未定义呆滞周期不默认标记呆滞。
- 金额遵守成本权限和币种；不同计量单位不直接相加；合并出库按来源分摊事实，不把整单金额算给单台设备。

### 工作台、审批、异常与提醒

- 我今天需要处理什么；待我审批的领料申请；某申请当前在哪个节点、谁可办理；被驳回的原因与处理记录。
- 某设备尚未消除的异常、登记时间、关联工单；异常次数和维修工单次数不能混加。
- 哪些提醒发送失败、发送给了谁：仅有通知管理权限的用户可查；不暴露邮箱凭据或渠道密钥。
- 只查询流程/提醒真实状态，不在对话中自动批准、驳回、撤回或发送催办。

### 跨业务与汇总

- P-103近期的维修、保养、点检、巡检、异常及实际用料概览；分别列出时间口径和授权模块，不把不可见数据描述成零。
- 今天/本周待处理事项按业务分组；某部门上月维修、保养、点巡检执行简报。
- 指标与明细可组合返回。简报里的每个数字来自后端，结论可追溯，不能让模型读取一页明细自行推算全量报表。
- “这个设备为什么总坏”“保养无效吗”是证据分析问题：可以列出实际记录、相关SOP和关联趋势，但不能把相关性写成故障因果结论。

## 领导管理视角补充

依据：用户明确要求考虑公司领导关心的数据和问题。以下加入本次需求与验收盘点，不代表指标已经存在；新增业务录入、外部系统对接和推断模型仍需分别确认。领导权限按实际角色授权执行，不因称谓自动扩大公司、部门、仓库或金额范围。

| 管理问题 | 代表问法 | 数据与解释边界 |
|---|---|---|
| 当前运行风险 | 今天有哪些关键设备故障？哪些事项需要我关注？哪些故障迟迟未恢复？ | 核对关键设备标识及故障/任务状态；不把所有报修等同停产，不凭模型定义风险等级。 |
| 趋势与改善 | 本月报修比上月多还是少？哪些设备、部门贡献了主要变化？保养和点检执行有没有改善？ | 同一口径、时间字段与完整周期对比；本月未结束时明确对照方式，不将部分月直接与完整月比较后声称变差。 |
| 维修响应与积压 | 有多少工单无人接单？积压集中在哪里？哪些等待最久？挂起的原因是什么？ | 区分派工、接单、处理、挂起、验收各阶段；有真实轮次/事件才计算等待，不把等待时长说成人员工时。 |
| 预防性维护执行 | 哪些重要设备保养逾期？哪个部门经常未按时点检？本月异常有没有后续处理？ | 复用已确认完成率和取消/延期/作废口径；关联缺失只报告未找到关联，不断言没有线下处理。 |
| 成本与资源 | 本月实际用料成本多少？哪些设备消耗最多、增长最大？维修成本中哪些费用未纳入？ | 先用已核实的实际物料消耗；未核实人工/外协费用时不得包装为完整维修总成本。币种、仓库和金额权限均保留。 |
| 人员与部门 | 工作量分布是否集中？哪些部门任务积压较多？某人承担哪些工作？ | 同时呈现任务数量、状态、样本和设备规模等可用背景；不能只按数量认定谁效率低，更不能自动得出绩效处分结论。 |
| 设备可靠性与更新 | 哪些设备频繁报修、重复出现同类问题？哪些设备值得进一步评估更新？ | 提供记录、设备年龄、消耗和分类事实；是否淘汰需可靠成本、替代投资、生产重要性等依据，不根据单一报修排名下结论。MTTR/MTBF按缺口清单处理。 |
| 备件保障 | 哪些备件可用不足？在修设备所需备件是否有库存？哪些物料长期没有流转？ | 使用实际预留/可用量和已配置阈值；未记录任务需求或替代关系时不推断必需备件，不默认给采购数量。 |
| 多公司管理 | 各公司报修、积压、保养和点巡检执行差异在哪里？哪些公司本月变化较大？ | 仅比较授权公司；原始数量与有依据的比率并列，不能因为设备数量多就认定管理较差。集团与公司管理员不自动共享全部数据。 |
| 管理简报 | 给我今天需要关注的事项；生成本月设备运维简报；上次关注的逾期任务现在怎样了？ | 简报按当前数据生成，每个数字可穿透；“上次关注”需真实历史上下文/对象，不凭模型记忆补造。定时推送需另有用户授权和通知配置。 |

### 管理回答结构

管理简报采用“范围与截止时间 → 主要事实 → 变化与贡献项 → 待处理事项 → 可核实的下一步”，避免堆一屏表格。默认提供少量最相关事项并可展开，依据用户关心的主题选择内容；未配置重要性或阈值时不自行打红黄绿风险分。

例如“本月设备管理情况怎样”：优先呈现有权限且数据可靠的报修新增/完成与当前积压、保养/点巡检执行及异常、实际物料消耗，明确哪些是期间数据、哪些是截至当前的状态。再按可核实变化展开设备/部门明细，不默认把所有模块金额和比例合成一个总分。

回答“为什么变差”时先给出分组贡献、异常记录和历史对比；因果证据不足则说明只能确认变化集中在哪些设备/故障类型，不能把统计相关性说成原因。任何建议标明依据，不能在同一回答中把建议描述为已经完成的派工、采购或审批操作。

### 外部数据依赖

停机造成多少产量/订单/利润损失、设备利用率/OEE、产能瓶颈、完整维修成本、更新投资回报等不能仅凭现有工单计算。需分别核实运行/停机事件、生产节拍与计划、质量产量、订单及财务成本等数据来源；本次列明需求与缺口，不默认为已经接入，也不擅自增加对接项目。

### 领导问题验收

在业务查询验收之外增加：今日管理摘要、月度简报、部分月同比/环比口径、变化贡献项、多公司同口径比较、权限缺失导致模块不完整、零基数、样本过少、关键设备未维护、人工费用缺失、未配置库存阈值和无法确认因果等场景。事实、推断、建议和数据缺口必须可区分。

## 3. 统一查询能力，而不是问题白名单

业务语义目录由后台注册，描述业务对象、允许字段、数据类型、操作符、时间字段、聚合方式、分组维度、排序、关联路径、单位及所需权限。模型只从当前用户可用目录生成受限查询计划，后台再次逐项验证。

- 操作类型：查明细、计数、分组数量/占比、已注册数值汇总/平均/极值、排行、趋势、同口径期间对比、查看详情。
- 条件：文本匹配、状态/关联对象选择、日期范围、数值范围、为空/非空；支持有界AND/OR组合及否定，按字段类型校验。不得忽略无法表达的条件。
- 关联ID：用户说出的公司、部门、人员、设备、计划等由本地选择服务解析；同名或范围歧义时提供候选供选择。不得凭模型猜ID，也不向模型发送全租户人员与组织目录。
- 分组：基础统计支持单维度和受限双维度；缺失归属明确“未填写/历史未归属”，分组保留稳定ID，父子组织/分类是直属还是含下级必须明确。
- 时间：相对时间按Asia/Shanghai计算，接口返回起止范围、截止时点和所用业务字段。未指定时间的当前状态查当前快照；涉及历史周期且没有可靠默认约定时只询问缺少的时间，不默认套一个月。
- 追问：保存上一轮已验证查询上下文；“只看白班”“按部门分”“改成上个月”“列出这些设备”改变相应维度，其他条件保留；“全部公司”“所有设备”等范围重置也必须被解析。不能只把几条原始问题拼给模型就假定上下文可靠。
- 复合问题：拆分为有界的多个只读查询，各自鉴权，全部条件可表达才执行；部分模块无权限时明确覆盖范围，不以未授权模块的数据参与跨业务计算。
- 数据执行：数据库内完成权限、筛选、分组、排序、计数和分页；严禁拉取全表在内存汇总或模型生成任意SQL。

共享的是语义解析、查询计划校验和结果呈现。设备、维修、保养、点巡检、库存分别保留业务适配Service和Repository，公共能力不能成为跨业务万能主表或任意SQL接口。

## 4. 回答与操作体验

- 数量：明确对象、范围、单位和截至时间。
- 列表：必要识别字段、状态、时间、20/50/100分页；编号进入原详情，返回保留上下文。
- 分组统计：表格展示分组、数量、占比；适用时附图；排行显示前N和其他项/全量总数，百分比明确分母。
- 趋势/对比：清楚展示当前周期、对照周期、时间字段和样本数；对照为0时不输出无穷大增长率。
- 统计穿透：统计与明细共用已验证查询，不允许点击图表后条件丢失。数据在两次请求间变化时标明查询时点，不能声称跨请求绝对静态一致。
- “报表发我”先在对话中呈现报表；只有明确要求下载时才走原导出权限与导出能力，不能因为能查看就自动授予导出。
- 知识与业务混合：实时查询走业务库；手册/SOP走知识库；明确展示数据出处。向量服务故障不应阻断不依赖它的业务查询。
- 不支持或数据不全：指出具体缺的是时间、对象、字段、数据来源或指标口径。允许执行的部分提供明确结果，不用一条笼统“不支持查询”应付全部问题。
- 全程不把业务数据推入向量库；除确需解释且已授权的最小资料外，汇总与列表由后端格式化，避免无必要地发送原始数据给外部模型。

## 5. 口径核查与不能擅自推断的项目

1. 维修报修、首次接单、本轮派工/接单、提交、验收、挂起和返工分别核对；处理等待、实际维修、停机、验收等待不能混用。
2. “故障次数”不能直接替代“工单数”。MTTR/MTBF缺少可靠数据时显示不可计算及原因，不写成0。是否新增运行/故障事件记录需另行确定，不能为回答一问擅加业务录入负担。
3. 保养与点巡检的完成、有效提交、按时提交、审核通过分别给出定义；延期、人工取消、自动超期作废、免检与跳过的分母按原业务规则，不能共用一个通用完成率。
4. 逾期是哪个截止时间、当前仍未完成还是曾逾期后已完成，必须从问题和口径中区分。
5. 点巡检计划部门与设备部门、负责人/候选人/实际点检人/审核人分开；现场开放任务无负责人不等于没有点检人。
6. 库存现存/可用/预留、发放/实际使用/安装/退料及实际成本严格沿用原口径；金额权限、币种和单位不能绕过。
7. 组织与设备更名、调部门后的历史归属按原业务保存事实处理；没有历史快照就说明按当前归属，不能伪称还原历史。

## 6. 实施顺序与完成标准

1. 按上述矩阵逐项登记“已有可复用接口 / 需新增SQL聚合或只读接口 / 数据或口径不足”，核对字段和权限，不先写一份庞大硬编码提示词。
2. 建设类型化目录、查询计划验证、本地关联对象解析和上下文追问机制；为实际业务分别接入适配层。
3. 一次补齐设备、维修、保养、日常点检、周期巡检常用基础查询与已确认口径的统计；并接入现有库存、待办、审批和异常的只读查询。缺数据项单列，不冒充完成。
4. 建设公共结果卡片、分组图表、分页、穿透和原有导出适配。已有公共表格/分页/导航优先复用，不改动无关页面布局。
5. 成组验收后交付已实现与未实现清单，附真实问法、预期查询计划、SQL对照、权限结果、截图和剩余数据缺口；不能以构建通过或一句问答成功代替验收。

### 成组验收要求

每个模块覆盖明细、计数、分组、时间、人员/组织/设备条件和追问。每种能力至少包含口语、规范用语、同义词/缩写、组合筛选、否定/OR、空结果和含糊请求的适用样例。矩阵是测试语料，不是运行时问句白名单。

- 固定原问法：“我们有多少个设备”“所有设备按照分类统计报表发我”“所有设备的MTTR、MTBF给我”。最后一项在数据未接通时应明确缺少什么，不能虚构或把它当知识库问题。
- 维修：“上月哪些还没接单”“按故障类型分一下”“只看某部门”“这些工单列出来”。
- 保养：“本周还有哪些没做”“各部门按时提交情况”“改成上个月”“列出逾期任务”。
- 日常点检：“今天白班还有谁没检”“哪些开放任务还没人做”“按班次统计异常”“这个点检人上周做了哪些”。
- 周期巡检：“这条路线哪里异常”“本月巡检任务完成情况”“列出未检检查点”，核对任务/设备/项目的粒度。
- 库存：“这个备件还能领多少”“这个设备上个月实际用料”“按仓库看库存”，核对金额/单位/仓库权限。
- 待办/审批：“我还有哪些待审批”“这张领料单到谁了”“我发起但被退回的申请”。
- 两公司同名部门、无权限公司/仓库、当前选中设备、切换设备、跨模块只部分有权、无成本权限、删除/作废、时间跨夜、零分母、历史组织变更均单独验证。
- 分类/状态空值、父子分类、双维分组、TopN其他项、百分比舍入、连接多明细导致重复计数、大数据分页与查询耗时必须检查。
- 模型超时、非法输出、不存在的字段/ID、提示注入和向量接口404：不能扩大查询范围、泄露敏感字段、执行写操作或重复调用。

验收中发现未覆盖的常用语义，应修正目录、解析或适配能力，并回归同类场景；不能只对该句新增专用分支。
