## 需求追踪与实现

| 场景 | 设计 / 实现 | 验收条件 |
|---|---|---|
| 标准保存引用历史备件 | MaintenanceService → 已有LegacySpareStockRepository.find → BaseMapper | 同租户存在性；按当前新增/编辑权限核对公司，不能借用查看权限并集；没有FOR UPDATE及库存写入 |
| 查看备件选项 | Service按原standards/plans/tasks查看菜单解析公司并集，Repository.listVisible落实租户与公司条件 | all仍只限本租户；空公司范围返回空，不借用部门/本人权限；不额外过滤零库存 |
| 对外格式 | MaintenanceLegacyStockOption五字段 | id十进制字符串；code/name/model原文本；quantity继续JSON数值，内部company_id不输出 |
| 旧协议兼容 | 原/maintenance/choices及paged参数，标准保存接口 | 根六字段不变；paged=true不读旧库存；备件汇总仍trim名称/型号并stripTrailingZeros，不扣减数量 |

删除MaintenanceRepository的loadLegacyStock/listLegacyStock及12行手写查询，Service直接使用自有库存仓储，不保留转发。没有新建通用仓储、Service或框架；复用已有LegacySpareStock实体及Mapper。选择列表仍按name排序，新增id作为同名时的稳定次级键。

原选择器先加载全租户旧库存，再逐行重复解析公司权限。新的公司并集来自服务端PermissionService，按与原companyAllowed相同的all/companyIds语义解析一次，并在SQL内过滤。标准写入继续独立使用新增/编辑scope，没有把可看等同于可用来保存标准。没有跨请求权限缓存。

旧库存仅供历史引用：新find是普通读取，不复用旧安装流程的lockStock；原lockStock/stocks方法不变，不重新开放旧库存入库或出库。数据库实际company_id/model/quantity均NOT NULL，保留空型号和decimal数量原语义；没有修改结构或精度。
