## 1. 目标与实施原则

整改目标是：打开一个业务类，能看清它负责什么、输入输出是什么、权限在哪里检查、事务在哪里结束，以及改动后应运行哪些测试。

沿用现有 Java 21、Spring Boot、MyBatis-Plus 分层单体，以及 Controller、Service、Repository 按层再按业务划分的目录。规范入口为[工程文档索引](../engineering/README.md)，本计划不另建一套工程规范。

实施原则：

1. 先建立行为基线，再修改结构；已发现的业务缺陷与保持行为不变的重构分别标识。
2. 先做一条完整样板链路，经用户审阅和验证后再推广。
3. 按业务职责拆分，不能只把长方法移入工具类，也不为减少代码行数合并不同业务。
4. 保留未涉及的用户改动；正在开发的审批等功能与本计划分别核对，避免混成无法审查的一批变更。
5. 保留库存成本口径、幂等保护、权限权威、锁顺序及事务边界。确需改变时单独说明证据、影响和验证安排。
6. 数据模型调整执行工程约定 ENG-44～ENG-51；本计划不因类型化或分层整理自动授权改库。
7. 性能以最终生成的SQL、执行计划和测量结果判断。不将“没有手写SQL”等同于性能差，也不将“搬进XML”等同于完成架构整改。

## 2. 审查依据与问题清单

本次进行了目录与代码结构扫描，并重点抽查设备、维修、保养、点巡检、库存、报表、权限和测试配置；不是逐行审计全部代码，也没有在本次只读审查中运行新的业务测试。

| 问题 | 具体依据 | 影响与处理方向 |
| --- | --- | --- |
| 固定业务过度依赖 Map | `RequisitionService.save`、保养接口使用 `Map<String,Object>` | 输入输出和必填项不清楚，类型错误留到运行时；优先类型化关键命令和结果 |
| Service 职责过多 | `InventoryFlowService`承载退料、调拨、盘点、期初和冲销 | 不同业务的状态、权限及库存动作交织；按真实业务边界拆分 |
| 服务双向依赖 | `RequisitionService`延迟注入`OutboundService`，出库服务又依赖领料服务 | 调用链和事务归属难以判断；提取真正共用能力，形成单向依赖 |
| SQL职责不一致 | `AnalyticsSourceService`、`AnalyticsAccess`构造SQL；分层检查的SQL禁止集合未覆盖`experience` | 报表与其他模块遵循不同约束；SQL归Repository并补检查 |
| 状态规则散落 | 不同服务分别维护状态集合及操作条件 | 新状态容易只改部分入口；每个业务集中维护自身状态及资格规则 |
| 查询契约不统一 | `AdvancedFilters`、`SqlListFilters`、普通参数与设备专用查询并存；公共`ListQuery`默认10条 | 参数处理和页大小行为不一致；统一基础语义，保留业务字段白名单 |
| 持续集成覆盖不完整 | MySQL CI任务显式运行`EngineeringQueryMySqlIT`、`SelectorMySqlIT` | 工作流、通知等专项验证不一定随提交执行；建立明确测试入口并检查跳过情况 |
| 测试与生产执行分支不同 | `RepairOrderService`有`workflow != null`分支，`RepairConcurrencyTest`传入null | 部分测试验证备用路径，不能充分证明生产路径正确 |
| 时间来源混用 | 报修编号月份指定上海时区，部分事件时间使用默认时区 | 在其他时区部署时可能出现不一致；明确时区并注入Clock |
| 金额隐藏依赖字段黑名单 | `InventoryMoney.hide`删除已登记名称 | 新增金额字段容易漏登记；属于扩展风险，不代表已证实泄露 |
| 名称反查关联ID的旧入口 | 维修旧操作入口通过姓名查用户ID，解析器拒绝重名 | 虽有保护，但重名会导致该入口不可用；新入口传ID，兼容解析集中管理 |
| 文件生命周期需要补核对 | 文件先写磁盘，再记录元数据，并处理部分失败补偿 | 仍需核对写入中断、进程退出和上传后放弃的文件一致性 |
| 部署配置缺少统一必填边界 | 出库预览密钥未配置时使用进程内随机值 | 多实例且未配置一致密钥时可能拒绝跨实例预览；按部署条件明确启动校验 |

关于JSON需要特别区分：代码出现`payload`、Map或JSON解析，不等于数据库仍以通用JSON持久化核心数据。例如库存已有具体业务表和类型化字段。审查时分别核对数据库权威数据、历史快照、兼容视图及服务层对象，不重复建议未经证实的改库。

## 4. 第一批：领料草稿样板

### 4.1 改动入口

- [RequisitionController](../../backend/src/main/java/com/windasoft/eam/controller/inventory/RequisitionController.java)：新增、修改与详情接口。
- [RequisitionService](../../backend/src/main/java/com/windasoft/eam/service/inventory/RequisitionService.java)：现有`save(Long requestId, Map<String,Object> body)`及关联读取。
- [RequisitionRepository](../../backend/src/main/java/com/windasoft/eam/repository/inventory/RequisitionRepository.java)：该链路所需的主单与明细读写。
- `dto/inventory`：新增明确的请求及结果类型，名称和字段在实施前按实际调用方确认。

选择这一链路，是因为它包含权限、公司、任务、仓库、版本、明细和事务，能够检验方案是否实用。第一批不直接改变实际出库记账算法。

### 4.2 请求从Map改成明确类型

目前的方法：

```java
save(Long requestId, Map<String, Object> body)
```

内部反复通过字符串取字段、转换类型：

```java
id(body.get("taskId"));
text(body, "taskKind");
(List<?>) body.get("lines");
```

计划采用的类型示意如下，尚未实施，完整校验与序列化配置将在实施时补齐：

```java
public record RequisitionDraftForm(
    TaskKind taskKind,
    Long taskId,
    Long warehouseId,
    String remark,
    List<RequisitionLineForm> lines,
    Integer rowVersion
) {}

public record RequisitionLineForm(
    Long materialId,
    BigDecimal quantity
) {}
```

- 修改时必须提供`rowVersion`，新增时不需要。
- Controller入口校验格式、必填项和嵌套明细；Service验证关联对象、状态、版本及权限。
- 数量精度、最大明细数、重复物料规则沿用当前业务约束，不因为换成注解而悄悄改变行为。
- 核对现有前端的ID及数量传输格式，使用契约测试验证反序列化兼容性。
- 租户、申请人、公司归属及单据编号由后台确定，不直接采信请求中的这些值。

### 4.3 Service公开入口表达业务动作

计划将新增和修改拆为清楚的公开入口：

```java
@Transactional
public RequisitionDetail create(RequisitionDraftForm form);

@Transactional
public RequisitionDetail update(
    long requestId,
    RequisitionDraftForm form
);
```

两个入口各自建立事务，共同步骤可放在私有方法中。不能依赖同一个类内部调用另一个`@Transactional`方法来启动事务。

内部编排按现有约束明确表达：

1. 取得库存互斥锁。
2. 修改时锁定原单，检查申请人、草稿状态和版本。
3. 锁定关联任务，检查任务资格和权限。
4. 锁定仓库，检查启用状态及公司一致性。
5. 按物料ID顺序锁定物料，验证明细。
6. 保存主单、明细及事件。
7. 返回类型明确的详情结果。

第一批保留现有事务及锁顺序。重复查询等性能优化另列改动，避免同时改变太多因素。

### 4.4 Repository一起类型化

核心主单查询计划返回明确类型，例如：

```java
public record RequisitionHeader(
    long id,
    long companyId,
    long warehouseId,
    long applicantId,
    RequisitionStatus status,
    int rowVersion
) {}
```

Repository负责SQL、行映射、计数、分页和批量读写；Service负责权限、业务资格和事务编排。字段类型以实际表结构及接口约束为准。

固定主单、明细和核心状态逐步使用明确类型；客户扩展字段等真实动态结构继续采用适当的动态对象。

| 场景 | 预期 |

## 5. 后续各问题的具体改法

### 5.1 拆分库存业务职责

从`InventoryFlowService`分别提取退料、调拨、盘点等操作服务，保留共享的库存记账、成本计算和锁定能力。拆分依据是业务职责及生命周期，不按机械行数拆文件。

领料与出库之间提取双方真正共用的资格校验及数据读取能力，形成单向依赖，再移除对应`@Lazy`。不新增包罗全部业务的通用管理器。

### 5.2 集中状态与操作资格

每个业务定义自己的状态类型和操作规则，列表按钮所需能力与后台操作基于相同业务规则计算。提醒及领料资格核对同一状态口径。

第一阶段保持现有数据库状态值和接口显示值兼容，不把改成英文状态码作为结构整改的前提。涉及持久化编码变化时单独做迁移设计。

### 5.3 整理查询、权限与报表

#### 5.3.1 技术决策与适用条件

采用“以现有MyBatis-Plus为主、复杂查询保留明确SQL、Repository对业务提供类型化访问接口”的方案。

选用方式以查询语义、表达是否清楚、现有实现及可验证性为依据，不机械按SQL行数决定是否迁入XML。最终SQL相同且执行条件相同时，仅改变Java字符串或XML的存放位置，不会自动改善数据库性能。

| 场景 | 默认采用方式 | 必须核对的边界 |
| --- | --- | --- |
| 单表增删改查 | MyBatis-Plus，使用实体字段引用 | 租户、逻辑删除、版本、更新字段及受影响行数 |
| 普通列表筛选／排序／分页 | 类型化查询对象＋MyBatis-Plus条件构造器 | 授权与筛选在数据库分页前完成；稳定次级排序；真实总数 |
| 复杂关联、分组统计、CTE及维修报表 | 自定义Mapper方法＋XML，映射为明确的结果对象 | 关联基数、空值、分组口径、计数、索引和数据库兼容性 |
| 当前页负责人、字典名称、附件等展示补充 | 数据库分页后，按当前页ID批量加载 | 不产生逐行查询；不借装配返回额外未授权数据 |
| 库存成本分摊、锁定及条件更新 | 保留可审查的显式SQL；新增或重构时优先评估Mapper XML | 锁顺序、锁范围、条件更新、防重和事务回滚，不机械替换为普通CRUD |
| 已有稳定JdbcTemplate实现 | 保留在Repository内，按模块逐步评估收敛 | 不仅为形式统一批量改写；迁移时验证结果、事务和锁行为 |

当前不增加另一套ORM或通用查询平台。MPJ联表构造器可以作为后续备选，但需由样板证明它能降低维护成本，并核对与当前依赖、权限、分页及数据库的兼容性后再决定，不因其他项目使用而直接引入。

#### 5.3.2 调用链与职责

```text
Controller：协议、请求及字段格式校验
    ↓
Service：业务规则、授权范围、事务及指标含义
    ↓
Repository：组织查询／批量装配，返回类型明确的结果
    ↓
Mapper：MyBatis-Plus或自定义XML，执行参数化SQL
```

Mapper继续放在既有`repository/<业务>`范围；采用XML的查询资源按业务归档在`resources/mapper/<业务>`。实施时核对当前扫描配置和架构测试，不新增与既有分层并列的另一套数据访问目录。

业务调用接口表达用途，例如以下设计示意：

```java
EquipmentPage findPage(
    long tenantId,
    EquipmentListQuery query,
    PermissionScope authorizedScope
);

RequisitionHeader lockById(long tenantId, long requisitionId);
```

上述类型及签名在实施时复用现有能力并按业务需要确认；不另建重复的权限模型。Service无需知道底层使用Wrapper还是XML，也不传递SQL文本。Repository承担实质的查询组织、映射或批量读取职责，不为每张表额外增加只转发方法的空壳。

Service中现有的SQL表达式和参数装配移入相应Repository／Mapper；业务授权范围仍由Service根据后台身份和权限确定。MyBatis-Plus、XML与保留的JdbcTemplate路径执行同一套已确认授权语义。

#### 5.3.3 关联查询与分页后的批量装配

必须在数据库分页前完成的事项：

- 租户和数据权限过滤。
- 影响结果集的部门、负责人、分类、自定义字段等条件。
- 按关联字段排序、聚合筛选、总数计算和分页。

可以在数据库分页后进行的事项：

- 为当前页设备批量补充负责人、字典名称、附件等展示信息。
- 使用已取得的当前页ID批量读取一对多明细，避免循环逐条访问数据库。

禁止先取一页，再在Java中删除不符合筛选或授权条件的记录。多个一对多关系不直接平铺连接后对重复主单分页；根据语义选择EXISTS、先聚合后关联、主单分页后批量装配等方式，并用数据验证。

统计必须明确计量对象，例如设备数、维修工单数或明细行数。列表总数、分组计数和导出不能因为关联扇出而重复计算；关联缺失及空值的处理也须与接口口径一致。

#### 5.3.4 SQL与参数安全

- 参数值使用MyBatis的`#{}`或现有JDBC绑定参数，不拼入SQL文本。
- 请求参数不得直接进入`${}`、`last`、`apply`或SQL字符串；确需动态片段时，只允许后台受控字段目录、排序白名单和经过校验的条件编译结果，值仍单独绑定。
- 表名、列名、排序方向及操作符不能由前端任意指定；未知字段或不支持的条件明确拒绝。
- 自定义字段继续复用现有类型化扩展值模型和条件能力，不为此增加可执行任意SQL的配置入口。
- XML公共片段仅复用真实一致的列或条件，不把不同业务堆成由大量kind分支控制的通用SQL。
- 同一查询族的列表、计数和导出复用一致的授权和过滤语义；不以复制三份WHERE条件长期维护。

#### 5.3.5 权限与事务验证

后台身份决定租户及可访问范围；请求内的公司、部门、仓库等条件只能缩小结果。空授权范围应拒绝或返回空集，不能因省略条件而查出全部数据。

保留显式授权检查。不能假定安装MyBatis权限／租户插件后，所有XML、JdbcTemplate、子查询、统计及导出自动受保护；逐类验证实际SQL与结果。是否进一步采用统一拦截器单独评估，不在重构中改变权限权威。

Mapper与保留的JdbcTemplate路径继续使用现有Spring管理的数据源和事务。涉及库存及工作流的迁移须验证共同回滚、连接参与、锁顺序与条件更新，不能仅凭使用相同数据库推断事务正确。

#### 5.3.6 三类样板与验收产物

以下是第4A批的查询专项样板，不替代第一批领料草稿业务链路。

| 样板 | 实施及检查内容 | 验收证据 |
| --- | --- | --- |
| 设备列表 | 核对现有重构实际实现，验证高级条件、自定义字段、关联字段排序、当前页批量装配 | 最终SQL、参数类型、实际总数与跨页结果、代表查询执行计划；验证20／50／100及导出批次 |
| 维修统计 | 明确时间与状态口径，将Service内SQL移至Repository／Mapper；返回类型化统计结果 | 明细与汇总可对账；无维修、重复关联、缺失关联、跨公司及无金额权限用例；实际执行计划 |
| 库存锁定 | 选择当前业务已使用的锁定及条件更新语句，明确签名、返回类型和SQL归属；不为样板强制迁移稳定实现 | 隔离MySQL下的重复提交、并发冲突、失败回滚及受影响行数；成本／数量及锁行为回归 |

每个样板向用户展示：改前／改后调用接口、代表实现、SQL及参数映射、权限进入位置、验证结果、性能观察与未验证项。

性能观察记录测试数据规模、索引、筛选选择性、数据库版本、执行计划、读取行数及耗时条件。只在同等条件下比较；不把少量夹具正确性测试当作生产规模性能结论，不预先承诺性能提升比例。

#### 5.3.7 推广门槛

样板通过用户审阅和必要验证后，第4B批逐模块推广。保留原URL、有效参数及返回契约，明确处理历史别名和非法输入；普通列表20／50／100与导出、内部批次分别管理。

同步扩展现有分层检查，禁止Controller访问持久层、Service持有SQL或越层访问Mapper；对既有未达标模块制定逐项收敛范围，不仅修改目录和类名来通过检查。

### 5.4 统一错误与时间口径

复用现有异常处理和`fieldErrors`，明确区分预期字段错误、权限拒绝、版本冲突和系统异常；不把数据库异常或编程错误统一包装成用户填错。

时间使用明确的业务时区和可注入Clock。业务日期、事件发生时间和持续时长分别表达，核对数据库会话及接口时间格式，并补跨月、跨夜、截止时间和提醒测试。

### 5.5 金额字段授权

在查询投影或响应装配时明确控制金额字段；现有黑名单作为补充保护。增加无金额权限的接口契约测试，覆盖列表、详情、导出及统计等受影响入口。

此项先核对现有权限口径，不增加新的成本权限概念。

### 5.6 测试与生产路径一致

必要依赖在测试中正常构造或模拟，不通过传null使服务执行另一套实现。兼容路径明确命名、单独测试，并记录退出条件。

CI为关键工作流、库存、通知等验证建立明确入口，使用隔离数据库；检查预期测试是否执行，避免环境变量未设置而静默跳过。

## 6. 需要单独说明取舍的可选事项

以下事项不混入纯结构重构自动实施：

| 事项 | 场景与收益 | 代价及前置条件 |
| --- | --- | --- |
| 调整库存锁粒度 | 测量证实租户级锁等待影响吞吐后，改善并发 | 必须先取得锁等待与事务耗时证据，重验成本、一致性及死锁行为 |
| 事件异步化 | 外部通知等非同步完成事项减少阻塞 | 必须定义提交后投递、防重与失败恢复；必须共同成功的业务更新仍留在同一事务 |
| 文件自动清理 | 处理上传后放弃、进程中断等孤立文件 | 先检测和报告，再确认保留期及清理范围；不直接删除未关联文件 |
| 多实例生产配置校验 | 避免不同实例使用不同预览密钥等配置 | 按实际部署方式确定生产必填项，开发默认值与生产约束分开 |
| 引入MPJ等额外查询依赖 | 大量同类联表查询经样板证明可更清楚表达时，减少重复 | 评估依赖、权限及分页兼容性，以及多一种查询表达方式的长期维护成本；当前不引入 |

## 7. 用户审查与每批交付

每批开始前提交：

1. 改动文件及公开方法签名。
2. 改前／改后的调用关系。
3. 保持不变的业务约束，以及确实需要改变的行为。
4. 对应测试清单、数据环境及回退方式。
5. 数据访问类改动说明选择MyBatis-Plus、XML或保留JdbcTemplate的理由；涉及SQL时展示参数绑定、授权条件和代表查询。

每批完成后提交：

- 实际diff与代表方法的完整实现，便于逐项审阅。
- 已实现的业务效果与相关文件。
- 已验证的命令、环境、结果及必要的浏览器证据。
- 未验证事项、原因、影响及遗留风险。

判断完成以实际业务行为和验证证据为准。编译成功、文件变短或增加测试文件本身，不等于整改完成。

## 8. 回退与范围控制

第一批原则上仅调整代码及契约表达，不需要数据库迁移。保留现有接口路由和响应格式，通过兼容适配承接旧调用方；适配层不得继续充当核心业务模型。

回退以批次为单位恢复相应代码，不删除用户业务数据。涉及后续数据库变更时，另行提供字段映射、存量核对、迁移与回退方案。

推荐先审阅并完成“领料草稿”样板链路，再根据实际代码和验证结果决定推广范围。

SQL存放位置与访问技术的调整按查询族回退，不改写已执行迁移，不删除数据；若测量后确需新增索引或改变结构，单独执行ENG-44～ENG-51审查并新增迁移。
