## 一、目标与边界

采用 Maximo 的核心分工：**标准定义怎么做，计划定义何时做，任务记录本次执行。**

本次分阶段完成：

1. 维修、保养、日常点检、周期巡检统一任务底层。
2. 在统一模型上实施日常点检新方案。
3. 接通工作台、设备档案、库存用料、扩展字段、打印及首页分析。

前台保留现有名称和菜单：**维修工单、保养任务、日常点检任务、周期巡检任务**，不改成统一万能页面。

已确认允许清理相关测试数据，不要求兼容旧点检计划。实施时限定清理范围；已有库存账、出入库分配、使用安装事实和成本记录不得随任务清理。与这些记录关联的任务保留并迁移。

本轮不统一标准和计划主表，不建设 Maximo 的复杂嵌套作业、资源调度或通用流程设计器。

## 二、统一任务模型与业务边界

### 1. 数据结构

采用 **`eam_task` 统一主表**，类型为：

- `repair`：维修。
- `maintenance`：保养。
- `daily_inspection`：日常点检。
- `periodic_inspection`：周期巡检。

主表保存任务编号、类型、公司部门、标题、状态、计划时间、实际时间、验收要求、版本及审计字段。编号继续使用各业务现有规则，不强行改成同一前缀。

按真实关系建设公共明细：

| 数据 | 设计 |
|---|---|
| 关联设备 | 任务设备表，支持单设备、多设备及顺序 |
| 任务人员 | 候选人、负责人、协同人、验收人的角色关联 |
| 作业项目 | 项目来源、名称、方法、结果类型、单位、上下限及证据要求 |
| 执行结果 | 带类型结果、选项关联、图片附件、不适用原因 |
| 提交与验收 | 每次提交及对应结果快照、验收决定与意见 |
| 用料与异常 | 关联现有用料、分配和异常记录，不重复建立库存事实 |
| 操作记录 | 操作人、动作、原因、时间及关联对象 |

明确的业务字段使用列或明细，不使用 `payload` 或整体 JSON 保存任务、项目和执行结果。

维修故障信息等独立职责建立专有明细；**不机械地为每种类型建立一张空壳详情表**。计划来源使用有外键约束的来源关联，避免一个 `plan_id` 无约束地指向多张表。

实施前形成字段字典、关系图、约束、索引及主要查询路径，作为数据库设计基线。

### 2. 状态与流程

主表只保留一份权威状态，使用稳定英文编码；各类型声明允许的状态及流转，显示名称支持多语言。

- 维修保留待派工、待接单、处理中、待验收、已完成等既有流程。
- 保养保留执行、暂存、提交、验收及无需验收直接完成。
- 点检保留执行、审核、免检、取消及补检规则。
- 周期巡检保留多设备执行、现有审核和路线语义。
- 验收决定统一使用 `accept／reject`。
- 超期与业务状态分开判断，不将“超期”混成另一套执行状态。

Controller → Service → Repository 分层不变。公共服务负责任务身份、版本、关联和公共读写；维修、保养、点检、巡检服务各自负责状态及业务规则，避免形成巨型公共 Service。

### 3. 权限与数据关联

- 保留各模块菜单、动作、数据范围及任务参与者访问规则。
- 任务类型不能成为绕过原模块权限的入口。
- 统一候选人员、实际执行人和跟进负责人含义，保留维修负责人、协同等既有角色。
- 库存用料逐步关联统一任务 ID；旧来源类型通过明确映射适配。
- 保留原库存分配 ID，领料、使用、安装仍各自记录，任务统一不产生再次扣库。
- 自定义字段继续按原业务对象配置，不因合表而混用四种字段方案。

## 三、日常点检能力

### 1. 一份计划、多条检查安排

主要服务操作工。主管配置“设备、项目、时间、人员”，操作工只看到当前应检事项。

每条检查安排包含：

- 适用设备和引用的检查项目。
- 一种调度方式及执行窗口。
- 候选执行人员、可选审核及跟进负责人。

支持按日、周、月、班次、每日多时段、固定小时／分钟间隔，以及人工事件触发。不同频次的项目建立不同安排；同一安排可覆盖多台设备。

日常点检类型用于分类，频次由检查安排决定。周期巡检的类型及周期规则保持现状。

### 2. 责任安排

提供三种方式：

| 方式 | 行为 |
|---|---|
| 指定操作工 | 可选择多人，其中一人完成 |
| 操作组 | 授权组内人员共享待办，其中一人完成 |
| 按排班 | 按业务日期、班次解析执行人员 |

- 默认指定操作工，不强制维护操作组和排班。
- 每份计划有跟进负责人，处理无人执行和超期。
- 设备级人员设置优先于安排默认值，页面显示来源。
- 点击“开始点检”时原子确定实际执行人；其他候选人同步看到处理中。
- 不同岗位必须分别检查时使用不同安排。
- 缺排班、无有效候选仍生成待安排任务并通知负责人，不静默漏掉。
- 转派和交接保留原因、人员及已录入结果。

### 3. 调度与现场执行

任务粒度为：**设备＋检查安排＋一次应检发生**。

- 固定起算调度，晚完成不顺延下一次。
- 支持跨夜班、工作日历、特殊开工日及停产免检。
- 月份不存在指定日期时跳过，预览中明确显示；休息日跳过，不累计补发。
- 保存前预览未来七天／三十天的应检窗口、设备、任务数及缺失人员。
- 调度中断后补齐发生记录，过期任务保留漏检事实。
- 开机前、停机后、换型后首期由人工发起，不宣称已经联动设备开停机。
- 后续预留自动事件、运行计量触发接口，本轮不建设采集平台。

操作工从工作台或扫码进入，连续填写本次项目；默认不把空白算正常。主动“全部正常”仅适用于允许批量判断的项目，不代填数值、照片。

默认允许逾期补检，保留真实提交时间；检查安排可禁止补检。后一时段正常生成，不能用一次检查抵扣多次要求。

### 4. 免检、异常与审核

- 停机不自动免检；主管按设备及时间范围批准免检。
- 未开始任务可免检，已提交任务不追溯免检；事后免检单列显示。
- 暂停计划停止未来生成，已生成任务通过明确操作处置。
- 标准及安排修改从后续任务生效，已生成任务不静默改写。
- 异常结果关联异常记录，重复发现可关联已有未消除异常，不自动重复报修。
- 检查完成与异常消除分开管理。
- 提供无需审核、整任务审核；多名审核人任意一人处理即可。
- 打回保留历次提交，及时性依据最终有效提交判断，验收等待不计入执行超期。

## 四、接口、切换与实施顺序

### 1. 接口及前端

保留现有业务 URL 和菜单入口，通过类型适配调用统一能力，避免一次修改所有页面协议。

- 公共任务 DTO 统一 ID、时间、版本、设备和人员角色。
- 各业务 DTO 保留专有字段；详情返回允许操作，由对应业务规则计算。
- 日常点检增加检查安排、调度预览、操作组、人工事件、开始、转派、免检等接口。
- 列表权限、条件、排序、计数、分页和导出在数据库执行。
- 统一查询作为工作台及跨业务读取能力，普通页面不得通过传入类型访问其他业务。
- 复用 Element Plus、公共表格、人员设备选择器、上传、扩展字段和字段错误。
- 不因本轮合表重做其他模块的页面布局。

### 2. 开发数据切换

新增 Flyway 迁移，不修改历史迁移。

先输出依赖清单及测试数据清理清单，备份后执行：

- 无库存、安装等受保护依赖的明确测试任务，可删除关联测试明细。
- 与库存等受保护记录关联的任务迁移保留，通过旧类型＋旧 ID 映射新 ID；不假定原表 ID 互不冲突。
- 旧点检计划不强行转换成新检查安排；被保留任务引用的来源保存为停用历史来源。
- 同步更新待办、异常、档案、打印、扩展值及分析关联。
- 对受保护数据核对数量、关联、金额和成本，不重算账务。
- 切换期间停止旧调度及任务写入；新服务成为唯一写入方，不长期双写。
- 新入口、数据核对和回归通过后，再移除失去调用方的旧实现。

规范中补充“统一执行对象”的边界，说明共享任务实体不等于合并不同标准、计划或使用 JSON 承载差异。

### 3. 分阶段交付

1. **统一模型与公共查询**：完成数据库设计、依赖清单、类型和权限映射、迁移及隔离验证。
2. **现有四类流程接入**：维修 → 保养 → 周期巡检 → 日常点检现有执行；接通库存、待办、档案和分析。
3. **日常点检新能力**：检查安排、频次、责任分配、生成、人工事件、免检及补检。
4. **一致性收口**：统计、导出、打印、扩展字段、多语言、旧实现清理和完整验收。

每阶段提供可运行结果；四阶段完成前不标记整体完成。

## 五、验收与交付

使用隔离数据库完成：

- 四类任务创建、执行、打回、重新提交、验收及无需验收完成。
- 维修派工接单、保养延期及下次计划、巡检多设备规则保持正确。
- 多频次、跨夜、节假日、无人排班、操作组并发开始和中断补生成。
- 免检、事后免检、漏检、补检及异常重复发现。
- 领料、预留、部分出库、退料、安装及用料成本关联不变。
- 公司部门范围、参与者访问、金额隐藏及跨类型越权。
- 列表、待办、档案、汇总、明细、导出和打印一致。
- 配置冲突、重复提交、失败回滚及调度幂等。
- 超过一万条隔离任务的分页、查询及执行计划检查。
- 1280×720、1440×900 下检查操作工执行、长项目、公共控件及固定底栏。

交付数据库结构文档、接口清单、数据清理与迁移报告、测试报告及关键截图，分别列出**已实现、已验证、未验证和已知问题**。
