# EAM 后端单一职责与数据访问规范 v1.0

> **状态**：2026-10-31 确立的后端专项规范。补充[后端开发规范 v1.0](../../../后端开发规范-v1.0.md)第 6—9 节，不替代现有工程约定、接口契约和已批准的领域规则。
>
> **适用范围**：Java 21 / Spring Boot / MyBatis-Plus 分层单体的新增或本次实质修改的后端代码。设备台账先做存量改造试点；其他模块的存量问题只在获授权的任务范围内渐进整改，不因本文件自动发起全仓重构。
>
> **执行状态**：本文件确立设计要求，不代表现有代码已经符合要求，也不代表自动化门禁已实现或运行。以实际检查、测试和验收结果为准。

## 1. 目标与判断标准

- 类的业务职责、依赖关系、数据写入归属和事务边界应当清楚；修改一个业务规则时，不应理解大量无关代码。
- **单一职责以变化原因和业务/数据边界判断**，不以类的行数、方法数、注入依赖数或“一方法一类”机械衡量。
- 正确性、权限与租户隔离、数据一致性、现有接口契约优先于结构形式。
- 优先复用已有组件、Mapper、Repository、DTO 和测试，不通过改名、加一层包装或转移代码行数掩盖复杂度。

## 2. 分层与依赖方向

| 层 | 应负责 | 不得负责 |
|---|---|---|
| Controller | HTTP 路由、协议适配、输入校验、响应封装 | 直接访问 Repository/Mapper、写 SQL、管理业务事务、跨对象业务编排 |
| Service | 按业务能力或用例处理规则、授权、状态与多对象协调，确定事务边界 | 直接使用 JdbcTemplate/Mapper/SQL，返回 HTTP 专用包装 |
| Repository | 明确持久化对象的数据访问、锁查询、批量读取与映射 | 业务授权决策、状态流程决策、跨对象写入编排 |
| Mapper | SQL 执行与数据库映射 | 跨业务对象流程编排 |
| Entity | 本系统业务表的持久化字段、类型与真实键语义 | HTTP 请求/响应、跨表视图、页面组合字段 |
| DTO / Command / View | 明确的请求、业务输入、只读投影及输出契约 | 代替应有的持久化实体或成为通用动态字段袋 |

正常依赖方向：**Controller → Service → Repository → Mapper / 数据库**。

- 一个业务模块可以有多个 Service；**一个 Service 可以使用多个 Repository**。
- Service 之间可根据实际业务职责调用，但避免循环依赖、层层转发和隐式跨事务行为。
- Repository 不得反向依赖 Service 或 Controller；原则上不以调用多个 Repository 的方式组织跨对象业务操作。
- 必要的底层持久化复用、批量查询和 SQL JOIN 不等于业务编排；判断边界时应看真实职责，而不是仅数依赖数量。

## 3. Entity、Repository 与数据归属

1. 本系统拥有、维护并直接读写的**每张业务表原则上对应一个独立的持久化 Entity**，准确表达字段、类型和真实主键。例外遵循现有后端规范：第三方框架内部表不重复建模；仅使用类型化查询投影的特殊情况需注明理由及边界。
2. 每个主要持久化对象应有**一个职责明确的主 Repository**。该对象的新增、修改、删除和数据访问规则集中维护，不应散落在多个无关 Repository 中。
3. 一表一主 Repository **不是**禁止只读 `*QueryRepository`，也不是要求表数量与 Java 类数量严格相等。一个 Repository 可以包含所属对象的多种查询。
4. Repository 可以通过所属 Mapper 或已有稳定的 JdbcTemplate 实现数据访问。简单 CRUD 优先 MyBatis-Plus；复杂查询使用明确 SQL 和类型化投影。复合主键须保持真实约束，以完整键及租户条件读写，不为套通用 CRUD 伪造单列主键。
5. **跨对象写入由 Service 协调**。例如设备创建同时涉及设备、负责人、子设备和 BOM，Service 调用各自 Repository，并在同一业务事务中完成；不让设备 Repository 代写其他对象的业务数据。
6. 允许合理的跨表只读 JOIN、聚合与分页专用查询。优先使用 SQL JOIN 或批量读取，禁止为了形式上的“一表一库”拆成 N+1 查询。
7. 多对象详情、列表及批量关系的装配属于查询 Service 或职责明确的映射组件。只读 QueryRepository 负责数据获取和投影映射，不混入写入流程与业务授权策略。
8. Repository 方法名表达**数据访问意图**，如 `findByTenantAndId`、`replaceOwners`、`countChildren`；不以 `approveOrder`、`checkPermission` 等业务流程名称掩盖规则归属。

## 4. Service 按业务职责拆分

- 按业务能力、变化原因和完整用例拆分 Service，**不按数据表数量机械拆分**。
- 设备台账候选职责：设备基础资料命令、设备查询、负责人、层级关系、BOM、附件、批量操作和导入。候选清单不表示必须创建八个 Service。
- 同一个业务用例可在一个 Service 中协调多张表；如果负责人或 BOM 尚无独立业务用例与规则，不应为了类名完整而新增空 Service。
- 当权限规则、状态流程、输入输出、事务边界或维护变化原因确实独立时，才提取相应 Service。
- 避免上帝 Service 和无意义的单行转发；提取前说明新的职责边界、调用方及维护收益。
- 不默认创建 `IService`/`ServiceImpl`、Facade、Helper、通用仓储基类或另一套分层框架。

## 5. 权限、事务与并发

- **事务属于完整业务用例的 Service 入口**。多个 Repository 的业务写入须原子提交或回滚；不得因拆分类而改变原事务边界。
- Service 依据可信身份上下文负责租户、数据范围、关联对象、业务状态与权限校验；Repository 接收必要的租户及授权过滤条件并在数据库侧执行，不自定授权策略。
- 保持既有乐观锁、唯一性约束、锁获取顺序、幂等语义、批量写入和导入回滚行为。先查重不能代替并发下的数据库唯一约束或原子条件更新。
- 注意 Spring 事务代理自调用、受检异常的回滚配置及 Service 间事务传播；不对所有方法机械添加 `@Transactional`。
- 外部文件系统、通知等副作用须与数据库事务明确协作，不能假定 `@Transactional` 会回滚磁盘操作或外部调用。

## 6. 查询、类型和性能

- 在数据库端落实授权过滤、查询条件、计数、稳定排序与分页；字段与排序使用白名单，SQL 值使用绑定参数。
- 对复杂列表、组合详情采用 JOIN、批量读取或类型化投影；禁止无依据地为每行重复访问数据库。性能结论须有真实 SQL/执行计划或代表性数据支持。
- 固定业务结构使用明确类型，不使用 `Map<String,Object>`、`Object`、`JsonNode` 贯穿业务层。真实的动态字段、历史快照或框架映射边界允许局部保留，并注明校验与转换位置。
- Entity 不直接作为 HTTP 请求/响应模型；负责人、BOM、历史等组合信息使用对应的 DTO/View。

## 7. 设备台账试点的审查与实施

**第一步只读审查，确认事实，再确定实施清单。** 覆盖设备台账 Controller、Service、Repository、Mapper、Entity、DTO、数据库迁移和测试。

重点核对：

- `EquipmentWriteRepository`：设备之外的负责人、字典、组织、用户、计数器及附件的数据访问归属。
- `EquipmentQueryRepository`：设备查询和其他领域读取、批量关联装配的边界，保证不引入 N+1。
- `EquipmentRelationsRepository`：是否存在不必要的跨 Repository 转发，以及子设备、BOM 和历史关系的真实数据归属。
- `EquipmentFileRepository`：数据库记录与磁盘文件操作的责任分离。
- `Equipment`：非持久化字段和 DTO/View 的边界；核查 `eam_equipment_owner`、`eam_equipment_history` 的类型化持久化模型。
- 现有 `EquipmentCommandService`、`EquipmentQueryService`、`EquipmentRelationsService`：按用例检视职责，并非仅因代码较长就必须拆分。

实施分批且每批可独立审查、验证、回退。每批明确：问题证据（文件/行号）、新旧职责对照、影响调用方、实际运行的验证命令和结果、未验证范围与剩余风险。

**兼容底线**：保持设备新增、修改、删除、批量、负责人、子设备、BOM、附件、导入、查询/导出，以及接口响应、权限、租户、事务、版本、加锁顺序与历史数据语义。此轮纯架构整理不修改数据库结构或既有业务规则。

## 8. 自动化架构门禁

优先扩展仓库已有的 `LayerDependencyArchitectureTest`、`LayerPackageArchitectureTest` 和设备专项测试，并接入已有检查入口，不另建孤立体系。

- 可自动化验证：Controller 不依赖 Repository；Service 不依赖 Mapper/JdbcTemplate；Repository 不反向依赖 Service/Controller；真实类依赖不循环；针对确认过的写入归属添加可执行约束。
- 必须结合代码审查：Service 职责划分是否合理、JOIN 是否必要、Repository 是否隐含业务编排、事务边界和锁顺序是否正确、抽象是否过度。
- 每条新门禁提供**违规反例应失败、合法正例应通过**的证据；存量例外必须写明具体位置、理由、适用范围与复核条件，禁止整包豁免。
- 测试要真实执行，涉及权限、并发及事务时以隔离 MySQL 集成测试验证。规则存在、测试文件存在、测试通过是不同状态，不得混淆。

## 9. 执行与变更纪律

- 新增和实质修改的相关代码遵循本规范；存量仅按明确授权范围渐进整改，不擅自扩大至全仓。
- 先检查现有公共实现、调用链、数据库结构和测试，再决定是否增加类或抽象。
- 如与已确认领域规则、现行后端规范或接口契约发生实质冲突，说明具体影响并先解决冲突，再实施相关变更。
- **规范集成、业务代码重构、自动化门禁落地是三个独立阶段**。仅完成规范文件时不得宣称既有业务代码已达标或 CI 已强制检查。
